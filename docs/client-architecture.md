# Client architecture

## Dependency injection and ownership

`App` is the composition root. Microsoft.Extensions.DependencyInjection registers one `ClientDatabase` and the settings, map, script, directory-cache, and protocol-history stores that use it, plus one singleton `IPasswordVault`; vault registration selects macOS Keychain, Windows Credential Manager, or Linux Secret Service. `MainWindow`, `SessionWorkspace`, and each `WorkspaceController` require those services by constructor injection. Consumers never resolve services from a global container and have no fallback constructor that creates a vault.

## Local persistence

`ClientDatabase` owns `wandur.db`, enables foreign keys and WAL, applies the schema inside a transaction, and exposes short-lived read connections plus serialized write transactions. World identity is stable across endpoint edits: profiles resolve an endpoint to a world ID, while maps and scripts are keyed by that world ID. Raw endpoint aliases are retained so legacy filenames using a trailing dot, Unicode spelling, or another equivalent host form can still be imported later.

The SQLite stores normalize searchable map fields (`area`, floor, coordinates, room IDs and directed link endpoints) and retain validated payloads for fields that evolve. Directory descriptions and artwork are cached in the same database. Historical GMCP/MSDP capability observations carry timestamps and are never treated as current negotiation evidence. Passwords and transcript content are intentionally outside the database.

Migration is lazy and idempotent. Existing files are read and validated before their rows are committed; originals are never deleted or rewritten. Per-source import markers and script tombstones prevent a later endpoint alias from resurrecting a deleted script or map. Use SQLite's backup API for future live backups when WAL sidecars exist; copying only `wandur.db` while the client is running is not a consistent backup.

Sessions have independent connection lifetimes. `SessionWorkspace` creates/owns the controllers for dynamic tabs and disposes them on tab/window close. Window composition creates view models with the current session and directory dependencies. The DI container does not retain disposable transient controllers after their tabs close.

## MVVM boundaries

- `ProfileEditorViewModel` owns editable fields, address normalization, cancellable directory suggestions, validation, save/remove commands and busy/error state. It uses `IWorldProfileStore`; `ProfileDialog.axaml` binds properties/commands. Code-behind only handles window lifetime and focus normalization.
- `PreferencesViewModel` uses `IClientSettingsStore` and an injected appearance-preview callback. `OptionsDialog.axaml` contains the presentation and bindings. Cancel restores the previous appearance; save preserves other settings changed by another session.
- `WorldLibraryViewModel` owns saved-world selection and add/edit/connect commands, and orders the list by `WorldUsage` (connections counted in `world_usage` and `world_connections`, weighted by recency) with a reorder that waits while the pointer is over the list. Its view formats rows, each with a `WorldThumbnail` (the directory's cached art or the world's initials), and handles pointer/key gestures.
- `WorldBrowserViewModel` owns directory queries, facet options, filtering/sorting, result selection, count/status/feedback and save/connect commands. Its view owns controls, images, layout and external-link launching.
- `WorkspaceController` remains the session presentation/application adapter: connection lifecycle, bounded output queue, prompt/private-input state, transcript/history and login coordination. It does not construct controls. An injected `ITranscriptDisplayFactory` creates the session-owned `ITranscriptDisplay`; the controller disposes it. The display adapter owns terminal emulation, rendering, scrolling and copy gestures. Core remains GUI-independent and retains its lightweight ANSI model for prompt/transcript analysis.
- `MainWindow` and `DesktopMenus` own native window/menu/dialog integration. OS dialogs, clipboard and Avalonia controls stay in the presentation layer.

Use CommunityToolkit.Mvvm for new observable properties and commands. Do not put persistence, networking, query algorithms or credential access in a view. Parameterless AXAML constructors exist for Avalonia's loader/designer; runtime composition passes a populated view model.

## Credentials and login

A world can save a username and opt into password storage and automatic login. JSON contains only the username, random password reference and prompt patterns. Vault keys bind the world ID, password reference, host, port, TLS choice and username. Changing those details requires re-entering the password; changing a display name does not.

- macOS: Security.framework generic-password APIs, without a shell.
- Windows: native `CredReadW`, `CredWriteW`, `CredDeleteW`, generic credentials persisted for the current user.
- Linux: `secret-tool` and a running Secret Service provider such as GNOME Keyring or KeePassXC. Install `libsecret-tools` on Debian/Ubuntu, or the package providing `secret-tool` on other distributions. Password input goes through stdin, never process arguments. A missing/locked store produces a readable error; there is no plaintext fallback.

Auto-login supports GMCP `Char.Login 1` password credentials when the server offers that method before the text handshake begins. It reads the existing endpoint-bound vault entry and sends credentials once. Missing credentials, disabled auto-login or unsupported methods receive `Char.Login.Credentials {}` to hand control back to the server. A rejected or unanswered structured attempt stops automation rather than retrying through text; the result timeout is 30 seconds. OAuth/browser login and reconnect tokens are not implemented or advertised. Incoming `Char.Login.*` frames remain private to scripts and the agent independently of echo state. Diagnostics separately shows redacted login offers/results and other incoming structured data during login.

The fallback is a one-shot, two-minute name/password handshake with configurable regex prompts. ANSI is parsed before matching; split packets and trailing newlines are supported. Sending a manual command cancels automatic login. Credentials bypass local echo/history. Normal Telnet still sends data unencrypted over the network; TLS must be supported by the MUD to encrypt transport. Account menus, MFA and other extra login steps remain manual.

New passwords use a new vault reference. If settings persistence fails, that newly created entry is removed. Replaced/forgotten passwords are deleted after settings save; cleanup failures produce a notice. The native macOS adapter is exercised with temporary credentials. Windows/Linux native stores still need execution on their respective systems.

## Diagnostics console · September 19, 2026

The Diagnostics page has a Console tab beside the protocol Messages and Observed fields. `Wandur.Core.Diagnostics.ConsoleLog` is a ring of the last 2,000 chunks or 512 KiB of the text stream the transcript receives, in the order it was written, plus sent commands and script echoes. `WorkspaceController.Console.cs` feeds it from the same three points that feed the transcript (the output flush, `SendCoreAsync` and the script echo callback), so protocol payloads never enter it. Privacy follows the protocol diagnostics rule: a chunk stamped private on receipt, or anything sent or echoed while input is private or a login is running, becomes one `[private]` marker (consecutive hidden chunks collapse), and remembered diagnostic secrets are masked by `ProtocolDiagnosticRedactor`, the same routine that scrubs GMCP and MSDP bodies. Rendering happens only in `Views/ConsoleView.cs`: each entry is a timestamp, a direction marker (`<<` received, `>>` sent, `[script]`) and the text with ESC as ␛, CR as ␍, LF as ␊ plus a real line break and other C0 controls as `^X`, in the plain mode of `DiagnosticsBodyEditor`. Appending is a ring insert; the view subscribes while loaded, only sets a stale flag while the page is hidden or Pause is on, catches up on the next layout pass or when Pause ends, appends new entries and removes evicted ones from the top of the document instead of re-rendering, and follows the end unless the reader has scrolled up. Copy puts the visible text on the clipboard, Clear empties the ring, and a new session clears it together with the protocol history.

The Messages tab filters the protocol history without dropping it: `ProtocolDiagnosticsViewModel` stamps every entry with its kinds (the GMCP package, every variable of an MSDP message read back from the formatter's JSON body, or the telnet option name for anything else), keeps the kinds seen this session as chips sorted by protocol then name with a count each (the first 24 shown, a "{n} more" toggle for the rest), and rebuilds the `Visible` list in one pass whenever a chip toggles or the filter box changes (case-insensitive substring over kind names and the formatted body, combined with the chips); Follow latest tracks the last visible entry, a selection survives while it still matches, the count reads "shown of total" while a filter is active, and Clear (also a new session) empties the kinds together with the entries.

## Localization

All client-owned natural-language labels, help, statuses and validation messages use `Wandur.Core/Localization/Strings.resx`, a strongly typed facade, and .NET ResourceManager satellite assemblies. Languages: English fallback, Spanish, French, German and Brazilian Portuguese. Preferences stores a language code; blank follows the system language. Unsupported system languages use English. Changes preview immediately, without interrupting connections. `UiLanguage.Culture` holds the selected resource culture explicitly so captured async execution contexts cannot freeze labels in an old language. `LocalizedText` provides key-based Avalonia bindings and emits a collection reset when the language changes; preferences restores the prior culture on Cancel. View models refresh computed labels through scoped subscriptions.

Server transcripts, externally supplied world descriptions/tags, player names, protocol commands and technical identifiers retain their source text. The offline demo is sample game content, not translated client chrome. Theme storage keys are stable while their display names are localized.

To change strings:

1. Add a descriptive resource key and a complete English sentence in `Strings.resx`.
2. Add all four translations. Preserve format arguments/specifiers and intentional newlines. Use separate singular/plural resources rather than concatenating English suffixes.
3. Run `python3 scripts/generate-localization.py` to regenerate the typed facade.
4. Reference `Strings.Key` from computed view-model values. For live UI labels use `Ui.TextKey(nameof(Strings.Key))`, `Ui.ButtonKey(...)`, `LocalizedText.Binding(...)`, or `{ReflectionBinding [Key], Source={x:Static loc:LocalizedText.Instance}}` in AXAML. Avoid capturing translated labels as immutable control values. Use `Strings.Format` for parameters; never localize protocol tokens or automation IDs.
5. Run tests. Resource tests require exact key and format-token parity and localized-dialog tests render all locales. `python3 scripts/generate-localization.py --check` detects facade drift.

The initial translations have automated coverage and layout checks; they have not been reviewed by professional translators.

## Mapping

`WorkspaceController.Mapping` coordinates room observations and movement evidence for each session. Its `RoomMapTracker` and protocol/text decoders live in Core. `IRoomMapStore` is injected from startup through the window and session factory; `MapViewModel` owns presentation and an isolated offline recognition exercise. See [the mapper guide](mapper.md) for supported formats and inference limits. `MapViewModel` partials separate editing and navigation commands; `RoomMapControl` draws a north-up viewport and forwards explicit edit gestures. Core owns validated JSON, directed weighted routes, map revisions/deletion tombstones, merge aliases and bounded undo. `WorkspaceController.Navigation` binds a verified walk to one session and its privacy epoch, with room acknowledgements queued beside transcript output before the next movement is sent.

### Room terrain inference

`Wandur.Core.Classification` runs the room-classifier model package locally: `RoomTextPreprocessor` reproduces the package's `preprocessing_spec.json`, `OnnxRoomEnvironmentClassifier` runs the encoder through ONNX Runtime one room at a time and applies the logistic head, and `ModelPackageInstaller` downloads/verifies packages by manifest hash into `models/room-classifier/<version>/`. `WorkspaceController.Inference` queues rooms without terrain onto a background worker and applies results on the UI thread through `RoomMapTracker.ApplyInference`, which stores `InferredEnvironment`/`InferredConfidence`/`InferredKey` on `MapRoom`. Presentation precedence lives in `MapEnvironmentPalette`: server or manual terrain first, inference second.

### Themes

`UserTheme.FromPreset` owns the shipped presets and `UserTheme.PresetNames` drives the picker, so a new entry appears in preferences, in duplication and in the tests without further wiring. Six are dark (Ember, Moonlight, Forest, Midnight, Slate, Rose) and four are light (Paper, Parchment, Daylight, Linen); `IsLight` selects the Fluent variant. Each preset supplies every key in `UserTheme.ColorKeys` plus a complete terminal palette for indices 0 to 15, and `UserTheme.DisplayName` maps the stable identifier to its localized name.

A world theme belongs to an open session. `SessionWorkspace.ApplyAppearance` reads the active tab's `WorkspaceController.WorldTheme`, so a world theme arrives when its session opens, follows the active tab, and gives way to the personal theme as soon as no active session carries one. Highlighting a row in the directory, in the saved world list or in the toolbar picker never changes the appearance; the preferences dialog still previews the personal theme live through `PreviewAppearanceSettings`.

Every entry point opens through `SessionWorkspace.OpenAsync`, which merges the cached catalog listing for that exact endpoint into the profile before the session starts, so a world whose saved profile predates its theme is themed on this open rather than on the next periodic refresh. The merge only adds: a listing that carries no theme leaves the saved theme in place, exactly as a missing protocol mapping keeps the last endpoint-bound copy. A directory service that has stopped supplying themes, or has not yet enriched a snapshot, therefore cannot strip the appearance of a world already saved with one. `RefreshCatalogProfiles` and the directory's save path follow the same rule, and a theme that only reaches the client on a later refresh is handed to the open session through `WorkspaceController.ApplyCatalogProfile`.

A theme change writes no new resource entries. Every write to `Application.Resources` raises a resources-changed notification that re-evaluates every DynamicResource in the tree, which measured about one millisecond per key and about seventy milliseconds per switch. `ThemeResources` keeps one brush per key for the life of the process and only moves its color, which leaves the resource dictionary untouched and repaints through the brush's own invalidation; the Fluent palettes, the theme variant and the dock grip drawing are rewritten only when they actually change. A headless switch with a session on screen now costs a few milliseconds. Because the bound properties no longer change identity, `ThemeService.Applied` tells consumers that read brush colors, notably `TranscriptDisplay`, to rebuild once and repaint.

`ThemeContrastTests` runs over every preset and enforces the readability rules: WCAG 2.x contrast of at least 4.5:1 for ANSI indices 1 to 15 against the preset's terminal background and at least 3:1 for index 0, main text at least 7:1 against the shell, muted text at least 4.5:1 and the accent at least 3:1. Hue identity is checked too, within 25 degrees of one canonical hue per role (red 0, green 140, yellow 55, blue 218, magenta 297, cyan 190), and each bright color has to stay visibly apart from its normal counterpart. Light presets darken and saturate their terminal colors, and their indices 7 and 15 become dark greys that keep the default-text role. A preset that fails these rules fails the build rather than shipping unreadable colors. The same test also checks the fallback palette against every preset terminal background of its own lightness, which is why Ember and Linen are the two it draws from.

### ANSI palettes

A preset's sixteen colors are chosen for that preset's own terminal background. A world theme, or a custom background color from the terminal preferences, can invert that lightness, and the preset palette would then be illegible: `ThemeService` therefore falls back to `UserTheme.PaletteForBackground`, which returns Ember's palette for a dark background and Linen's for a light one. A custom theme keeps the colors its editor shows, including over a world theme.

`TextStyle` retains the ANSI index alongside its default RGB value. The terminal adapter binds palette resources to XTerm theme options, so changing themes recolors existing output without replaying network data. Explicit RGB colors have no index and remain literal. Each `UserTheme` stores an optional dictionary of overrides for indices 0–15; omitted entries use `AnsiPalette.Defaults`, so older saved themes remain valid. Personal ANSI overrides remain active when a world supplies its own chrome theme. Palette drafts are deep-copied at load, duplicate and save boundaries.

## Dedicated terminal display · September 17, 2026

Avalonia 12.1.2, Dock 12.1.0.6, AvaloniaEdit 12.0.0, and Iciclecreek.Avalonia.Terminal 4.0.2 are pinned in package lock files. Desktop headless tests use xUnit 3 as required by Avalonia 12; Core tests remain xUnit 2.

`AnsiTerminal.OutputAppended` distinguishes server output from literal local echo. Its explicit `Cleared` event resets the display on user clear/reconnect; parsed server erase sequences do not fire it. `TranscriptDisplay` feeds each chunk once into the session's terminal, including while detached. Display buffers retain 2,000 scrollback rows plus the viewport; exported text comes from that buffer and joins soft-wrapped rows. The separate command field, scripting privacy gates, protocol handlers, and mapper keep their existing ownership.

`TerminalStreamFramer` retains incomplete controls (bounded at 8 KiB) so local echo cannot finish a fragmented server escape. Local echo preserves server attributes and the server's saved cursor. The embedded control has no process/PTY, disallows server clipboard and window operations, and currently disables terminal image protocols. We supply copy/select-all shortcuts because upstream's input path assumes a PTY.

`MudTerminalSurface` initializes the engine before the first visible tab, retaining output that arrives early. Text blink is default-off and independent of the separate input's cursor. Its visible-only timer temporarily conceals blinking cells for rendering and restores attributes immediately, preserving selection/export and server state. This adapter uses the default Avalonia rendering path and UI-thread writes; enabling upstream's threaded PTY or direct Skia path would require reviewing that assumption.

## Channels · September 20, 2026

Channel traffic is mirrored, never moved. `WorkspaceController` still writes every received line to the transcript untouched; the classifier only decides what may also be shown in the docked Channels panel, so closing the panel or getting a rule wrong can never lose output.

Channels come in two kinds. Protocol channels need nothing: a world that speaks GMCP names its own channels through `Comm.Channel.Text`, which is routed by its own `channel` and `talker` fields, and the printed copy of the same line that most worlds send a moment later is dropped on an exact text match within one second. Text channels are the rest, lines the world prints in a shape its admins change at will, and those are taught per world from the transcript. The shipped family rules are only a default for worlds nobody has taught yet; nothing world-specific belongs in them.

`Wandur.Core.Channels` holds the recognition. A `ChannelRule` is a channel name, a .NET regular expression with the optional named groups `speaker` and `text`, the command prefix that speaks on that channel (`ooc`, `gossip`, `tell {speaker}`), whether the channel is private, whether the rule is an exclusion, and whether it is disabled. Its JSON shape is the one a channel pack will carry and the one the profile stores today, `{ "channel", "pattern", "reply_command", "private", "exclude", "disabled" }`, the last three omitted when false; `families.json` uses the same keys. A `ChannelRuleSet` is an ordered list: patterns are anchored to the start of the line, matched against the ANSI-stripped text under a 50 ms timeout, and the first rule that matches wins, so a line is never two messages. An exclusion anywhere in the set wins over every other rule, a disabled rule is listed but never consulted, and an unreadable pattern is dropped rather than fatal. A captured speaker is cleaned before the check that it is a name: a leading `@` (account holders on Legends of the Jedi), a trailing role tag (`Nield [IMM]`) and the brackets of a description (`[A Human male]`) are decoration, so a taught pattern can capture them and the panel still shows the name. Prose whose "speaker" holds digits or punctuation is left alone.

Precedence: `ChannelFamilies.For(worldRules, codebase)` builds the set as the world's own rules followed by its family's, so a world rule beats a family rule for the same line and an exclusion taught on the world beats both. The families live in the embedded `Channels/families.json`, keyed by codebase family (`smaug`, `swr`, `diku`, `rom`, `circle`, `lp`, `generic`), with `{"include": "<family>"}` for inheritance; `ChannelFamilies.Match` maps the directory's free-text codebase onto a family. `ConnectionProfile` carries `Codebase`, merged from the catalog listing on open the same way a world theme is, and `ChannelRules`, a `ChannelRuleList` compared by content so a rule change is a profile change.

Teaching. `ChannelRuleProposer.Propose(line, second?)` is the heuristic behind the dialog, pure and unit tested. It reads one ANSI-stripped line as head, speaker, separator and text: it looks left to right for a name (`@?[A-Z][a-z]+`, optionally followed by a role tag `[IMM]`) that is followed by a separator, which is up to three words of verb and then a colon, a quote, a comma and a quote, or a prompt arrow (`: `, ` tells you '`, `, '`, `OOC: '`); when no name works it looks for a bracketed description (`[A Human male]`) with an optional tone in parentheses; and when neither works the leading tag or word is the head and the rule has a text group only. The head becomes an escaped literal with digit runs generalised to `[0-9]+` (`CommNet 0 ` is `CommNet [0-9]+ `), the speaker becomes `@?[A-Za-z]+` (plus `(?: \[[A-Za-z]+\])?` when a role tag was seen) or `\[[^\]]+\]`, the separator stays literal (with the tone as `\( ?[^)]*? ?\)`), and the text runs to the end of the line inside whatever quote opened it, but only when the line closes that quote. The channel name is the first word of the head lowercased (`ooc`, `chat`, `commnet`), else the separator's verb with its plural s dropped (`tells you` is `tell`), else `channel`; the reply command is the channel name, with ` {speaker}` for tells, whispers and pages, which are private. With a second example the pieces are narrowed to what both share: equal pieces stay, a tone one line lacks becomes optional, and heads or separators that differ become an alternation. `Compose(head, speaker, separator, closing)` rebuilds the pattern from edited pieces as `^head(?<speaker>speaker)separator(?<text>.*)closing$`.

The flow. `MudTerminalSurface` takes the right button before the terminal library sees it (the library would copy or paste) and raises `MenuRequested` with the logical line under the pointer, wrapped rows joined, and the selection if any; `TranscriptTailPane` does the same for the row under the pointer in the live view. `TerminalView` opens a context menu at the pointer with `Copy` (when there is a selection; the selection is left in place) and `Mark as channel...`, which opens `MarkChannelDialog` over `MarkChannelViewModel` for the first selected line or the line under the pointer, with the second selected line as the narrowing example. The dialog shows the example, the three piece patterns (editing one recomposes the rule; editing the rule directly leaves the pieces alone), the rule, a picker of the channels this world's set already knows plus `New channel...` with a name box, the reply command and privacy, and a live preview: the last 200 transcript lines run through the rule as it stands, with the match count and the first five matches as speaker and text, so over- and under-matching are visible before anything is saved. `Save` calls `WorkspaceController.TeachChannelRule`, which appends the rule to the profile's `ChannelRules`, saves through the settings store like any profile change (a world opened from the directory but never saved is saved by this, since the rule needs a profile to live on), and lets `ApplySettings` reconfigure the classifier, keeping the line in flight; the same path picks up rules saved in the world editor or another tab. `Not a channel`, offered when the line currently classifies as one, saves the same pattern as an exclusion for that channel instead. The demo session has no profile and cannot be taught.

Management. The world editor (`ProfileDialog`) has a Channels section, `ChannelRulesView`, listing the world's rules as cards with the channel, pattern and reply command editable, an enabled toggle, an exclusion or private tag, and a delete button; the profile's own validation refuses an unreadable pattern on save. There is no regex builder beyond the teaching dialog.

`ChannelClassifier` buffers received text into complete server lines through a two-line `AnsiTerminal`, so a network chunk that ends mid line waits and the panel keeps the styled runs the transcript already parsed; its `Rules` can be replaced mid stream. A following line that starts with whitespace extends the message above it. The controller runs this on public output only, behind the same privacy gate as the agent feed, and raises `ChannelMessageReceived`. The agent's chat filter asks the same classifier, so the agent and the panel always agree on what chat is.

`ChannelsViewModel` keeps an `All` tab plus one per channel, created on first message, with private channels ahead of open ones and an unread count on every tab that is not being shown. `ChannelsView` renders each message with the transcript's own run renderer through `TerminalPalette`, with a muted timestamp and the speaker in bold, newest at the bottom, following new arrivals unless the reader has scrolled up. The reply box sends `ReplyCommand + " " + text` through `WorkspaceController.SendAsync`, substituting the last speaker for `{speaker}` on a private channel, and refuses while private input is on or the session is disconnected. `WorkspaceFactory` docks it under the map on the right, closable and on by default, and `ClientSettings.ShowChannelsPanel` owns that default until the View menu overrides it for the session.

Collapsing channel lines inside the transcript with a custom renderer is deliberately not done. The owner's decision was to give the channels a panel of their own and leave the lines where they are.

## Inline completion · September 19, 2026

The composer offers a grayed completion after the typed text, learned from the session itself. `Wandur.Core.Input.CompletionTrie` is a case-insensitive prefix trie over UTF-16 characters: keys are lowercased, each terminal node keeps the casing the word was last seen with, a sighting count and a caller-supplied recency stamp, and it is bounded to 20 000 entries and about 400 000 nodes. Crossing a bound triggers one sweep that rebuilds the trie from the newest nine tenths of its entries, so no single insert pays for eviction. `Suggest(prefix, limit)` orders candidates by recency, then frequency, then length, never returns the prefix itself, and wants at least two characters.

`CompletionLearner` owns one trie per `WorkspaceController` and is replaced with the history on every world change, so the words of one world never leak into another. It buffers received text into complete lines through a two-line `AnsiTerminal`, exactly as the channel classifier does, and takes tokens of letters, digits, apostrophes and hyphens that are three to thirty-two characters long and not digits alone; the words of one line share a recency stamp, so among them the most frequent ranks first. The controller feeds it from the same public-text path as the agent and the channels, behind the same privacy gate (`IsPrivate`, a pending login), and skips any line that carries a remembered diagnostic secret. Sent public commands are learned the same way, and whole command lines come straight from `CommandHistory.Entries`, which already excludes private input.

`CompletionSuggester` decides what to show: when the draft is a prefix of an earlier command line, the rest of the most recent such line (line mode); otherwise, when the word being typed has at least two characters, the rest of the best trie candidate (word mode); nothing while private, with an empty draft, or with the caret away from the end. `TerminalView` renders the result as a muted `TextBlock` named `CompletionGhost`, laid over the command box in the same grid cell and placed after the typed text by asking the box's own `TextPresenter` layout for the caret position, translated into an overlay inset by the box's border and padding; it is never part of the text, so it cannot be selected or sent. Tab, or Right arrow with the caret at the end, appends the ghost (the typed prefix stays as typed, the remainder arrives in the casing last seen, so `wom` and a seen `Womprat` give `womprat`); Escape hides it until the draft changes; every other key keeps its meaning, and Tab only leaves the composer when no ghost is showing. The footer hint names Tab while a ghost is visible. `ClientSettings.ComposerSuggestions` (Preferences, Input) turns the feature off and applies to open sessions on save.

## Scripting runtime · September 19, 2026

One worker process per session, one Jint engine per script. `WorldScriptLibrary` owns a `SessionScriptWorker` (`Services/SessionScriptWorker.cs`), the client of that process: it starts the process through `IScriptRuntimeFactory` when the first script loads, ends it when the library stops, is disposed or changes world, and restarts it when it dies. Each `SessionScripts` keeps its public surface (run, stop, publish, feed, commands, ticks, status, log) but owns no process; it holds the script id (the `WorldScriptEntry.Id` Guid as a string) that names its engine inside the worker.

`ISessionScriptHost` (Core, `ScriptContracts.cs`) is the per-session worker client: `SeedAsync` sends the host's protocol cache, `LoadAsync(id, source, restricted)` creates or replaces one engine, `DispatchAsync(ids, event)` delivers one event to a list of engines and returns one result per id, `StopAsync(id)` discards an engine, `Stop` ends the process. `ProcessSessionScriptHost` speaks the line protocol to `Wandur --script-worker` over stdin and stdout, one request outstanding at a time, with a deadline of two seconds plus half a second per further engine in the request; a missed deadline, an unreadable reply or an exit kills the process and raises `Failed` once. Every result is validated per script against the per-event limits before the host acts on it. The worker side is `ScriptEngineSet` (`ScriptWorker.cs`), a dictionary of engines that handles `load`, `dispatch`, `stop`, `state` and `shutdown` on one thread, so no script's callbacks interleave with another's; the in-process test hosts use the same class. Each engine keeps Jint's per-callback constraints (300 ms, 100000 statements, 64 MiB, recursion 64, regex 100 ms), so a runaway callback fails only its own engine: the reply carries an error for that id, the host takes the same `Fail` path as a script exception, and the other engines keep going.

Ordering: every request of a session goes through one queue in `SessionScriptWorker`, including loads and stops. A published event is queued once with no target and fanned out when it is dispatched to every script that is running at that moment; a command, a tick, a key or a panel callback targets one script. Because a load sits in the same queue, an event published while a script is loading is dispatched after its engine exists and reaches it, and the seed is taken from the host cache at the moment the load is dispatched, so nothing falls between the seed and the running state. That is why the boot backlog `SessionScripts` used to keep (`_startup`, `LatestPerKey`) is gone. The seed is sent to the worker before a load whenever the cache has changed since the last seed, and the worker applies it to running engines through the no-callback seed path and keeps it for engines created later. Up to 1024 events may wait for the worker; past that every running script is stopped with the overflow error.

Crash recovery: when the process fails, every running or loading script is marked failed with the worker-failed message and the library re-runs the enabled ones among them from scratch on a fresh process, seeded again from the host cache. At most three restarts in five minutes; the fourth failure leaves the scripts stopped with `ScriptWorkerRestartLimit` shown. Tests: `ScriptRuntimeTests` (Core) covers the protocol with two engines, seeding before and after a load, per-script isolation of a runaway callback, the deadline and an exit; `SessionWorkerTests` (Desktop) covers one process per library, fan-out order, isolation through the library, the restart budget, late seeding and the real `Wandur.dll --script-worker` process killed from outside.
